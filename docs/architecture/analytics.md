# Analytics Architecture

Sprint 3 turns the click-event foundation from Sprint 2 into a production
analytics system. This document covers the pipeline end to end.

## 1. Pipeline overview

```
Visitor
  → GET /{shortCode}                    (redirect-route.ts)
  → RedirectService.resolve()           (Redis cache → Postgres fallback)
  → 302 redirect sent immediately
  → ClickEventProducer.enqueue()        (fire-and-forget, never awaited)
  → BullMQ queue "link-clicks"
  → ClickEventProcessor.process()       (async worker, separate from the request)
      → validate job data
      → parse user agent (device/OS/browser + bot detection)
      → resolve geography from IP (never persists the IP itself)
      → classify referrer (direct/search/social/referral/other)
      → extract utm_* query params only
      → compute a privacy-safe visitor hash
      → INSERT ClickEvent (idempotent — see §3)
      → upsert-increment LinkDailyStat (same transaction)
  → AnalyticsService                    (raw SQL aggregation, Redis-cached)
  → AnalyticsController                 (8 REST endpoints, RBAC-protected)
  → Dashboard / API consumers
```

**The redirect response never waits on any of this.** `ClickEventProducer.enqueue()`
is called but not awaited, and its own promise is wrapped in `.catch()` so
even a synchronous failure to reach Redis cannot throw back into the
request handler. This is verified by an e2e test that breaks the queue's
`add()` method entirely and confirms the redirect still returns 302
(`test/analytics.e2e-spec.ts`, "Redirect resilience").

## 2. Event lifecycle & idempotency

Every click event carries an `eventId`, generated by `ClickEventProducer`
at enqueue time (not by the database). That same value is used as:

1. The BullMQ **jobId** — BullMQ itself refuses to enqueue a second job
   with an id already present in the queue.
2. The ClickEvent **primary key** — if a job is _retried_ (crash mid-
   processing, transient DB error, worker restart, ...), the processor's
   insert attempt fails on the unique-key constraint instead of creating
   a duplicate row. That failure is caught and treated as a successful
   no-op, **including skipping the LinkDailyStat increment**, which
   already happened on the original successful attempt.

Retry configuration (`ClickEventProducer`): 5 attempts, exponential
backoff starting at 1s. Malformed job data (missing required fields, an
unparseable `occurredAt`) is discarded immediately rather than retried —
retrying data that can never become valid just burns the retry budget.

Failed jobs are retained for 7 days (`removeOnFail: { age: 7 days }`) for
investigation; completed jobs for 24 hours.

## 3. Data model

### `click_events` (raw, source of truth)

One row per successfully-processed click. See `schema.prisma` for the
full column list. Notable design choices:

- **No `ipAddress` column.** The raw IP is used transiently (to compute
  `visitorHash` and resolve geography) and then discarded — it is never
  written to any table.
- **`visitorHash`**, not a visitor ID: `SHA256(salt : ip : userAgent : UTCday)`.
  See §4.
- **`queryParams`** only ever contains recognized `utm_*` keys — never
  the full query string, which could carry PII (emails, tokens, ...).

### `link_daily_stats` (UTC-day rollup)

Maintained incrementally, in the same transaction as each `click_events`
insert. Exists purely as a fast path for the highest-frequency chart
(clicks over time); every other breakdown (referrers, geography, devices,
...) is computed directly from `click_events`, which stays the single
source of truth. This table is UTC-only by design — a non-UTC timezone
request bypasses it and aggregates raw events instead (see §6).

### Migrating to ClickHouse later

`click_events` is the table that would move to a column store if volume
ever demands it — `AnalyticsService` already talks to Postgres exclusively
through parameterized raw SQL (not Prisma's query builder), which keeps
the query surface small and portable. `link_daily_stats` is tiny by
comparison and would likely stay in Postgres either way.

## 4. Unique visitors

`visitorHash = SHA256(salt : ipAddress : userAgent : UTCday)`.

- The raw IP is **never persisted** — only this hash is stored.
- Including the calendar day is deliberate: the same visitor gets a
  **different** hash on a different day. This means LinkIQ cannot track a
  visitor's behavior across days even in aggregate — a real privacy
  property, not just an implementation detail — at the cost of counting a
  visitor who returns on a later day as an additional "unique."
- **Limitations, stated plainly:** the same visitor on a different
  network (wifi → cellular) counts twice; different visitors behind the
  same NAT with an identical browser count once; this is an
  approximation of "roughly how many distinct people," the same class of
  trade-off every cookie-less analytics approach makes.
- The salt (`VISITOR_HASH_SALT`) is configurable and should be set in
  production. Rotating it changes all _future_ hashes; historical events
  are unaffected since their hashes were already computed and stored.

## 5. Bot detection

`isbot` (known crawler user-agent patterns) plus a rule that a **missing
User-Agent is itself treated as a bot** — real browsers always send one.
`ClickEvent.isBot` is set at processing time. Every analytics endpoint
defaults to **human-only** traffic (`includeBots=false`); the overview
endpoint is the one exception, since it explicitly needs to report both
human and bot counts side by side.

## 6. Timezone handling

Timestamps are stored in UTC throughout. `AnalyticsQueryDto.timezone`
(IANA name, e.g. `America/New_York`) affects only how range boundaries
and time-series buckets are computed:

- Range resolution (`resolveDateRange`, `startOfDayInTimezone`) uses only
  the built-in `Intl` API — no extra date library — and is verified
  against real DST transitions in `date-range.spec.ts`.
- Time-series bucketing uses Postgres's own `AT TIME ZONE` machinery
  (`date_trunc('day', "occurredAt" AT TIME ZONE 'UTC' AT TIME ZONE $tz)`),
  which is why that query runs as raw SQL rather than through Prisma's
  builder — there's no equivalent there.

## 7. Privacy & security

- No raw IP address is ever persisted (see §3, §4).
- No cookies, tokens, or authentication material ever reach an analytics
  record — the redirect endpoint that generates these events is
  unauthenticated by design (it's what visitors click).
- `queryParams` is allow-listed to `utm_*` keys only.
- User-Agent strings are capped at 512 characters in storage.
- Every analytics API response is scoped by workspace membership
  (`WorkspaceRolesGuard`), enforced server-side regardless of what a
  client requests — verified by e2e tests that assert cross-workspace
  requests return 403 with no data.
- Redis cache keys are namespaced by workspace ID as a structural
  property of `AnalyticsCacheService.buildKey`, not a convention that
  could be bypassed by a call-site bug.

## 8. Caching

`AnalyticsCacheService` caches computed **aggregate** responses only —
never raw events — for 60 seconds per unique (workspace, endpoint, query
params) combination. A cache miss or a Redis outage falls back to
querying Postgres directly (never throws). See `analytics.e2e-spec.ts`
for cache-hit and cross-workspace-isolation tests.

## 9. API reference

All endpoints require `Authorization: Bearer <token>` and
`X-Workspace-Id: <workspaceId>`; VIEWER role or above. Full request/
response schemas are in Swagger at `/api/v1/docs` once the server is
running.

| Endpoint                           | Purpose                                  |
| ---------------------------------- | ---------------------------------------- |
| `GET /analytics/overview`          | Total/human/bot clicks + unique visitors |
| `GET /analytics/timeseries`        | Clicks bucketed by hour or day           |
| `GET /analytics/links`             | Top links by click volume                |
| `GET /analytics/referrers`         | Top referrer domains + category          |
| `GET /analytics/geography`         | Top countries and regions                |
| `GET /analytics/devices`           | Device type breakdown                    |
| `GET /analytics/browsers`          | Browser breakdown                        |
| `GET /analytics/operating-systems` | OS breakdown                             |

Common query params: `linkId`, `range` (`today`/`yesterday`/`7d`/`30d`/
`90d`/`custom`), `from`/`to` (custom range), `timezone`, `includeBots`.
`timeseries` additionally accepts `interval` (`hour`/`day`).

## 10. Local development

### Running the worker

The analytics worker (`ClickEventProcessor`) runs **inside the same Nest
process** as the API — there's no separate worker binary to start. Once
`npm run start:dev` (or the production `node dist/main.js`) is running,
BullMQ's `Worker` is already listening on the `link-clicks` queue.

### GeoIP provider

Defaults to `geoip-country` (an offline, bundled country-level database —
no network calls, no API key). Set `GEO_IP_PROVIDER=none` to disable
geographic resolution entirely (all events report `country: null`).

### Visitor hash salt

Set `VISITOR_HASH_SALT` in `.env` for anything beyond local development;
see `.env.example`.

### Seeding demo data

`npm run prisma:seed --workspace=apps/api` seeds ~30 days of realistic,
varied click events (multiple countries, devices, browsers, referrers,
and a modest bot-traffic slice) for the demo account's links, in addition
to the accounts/links seeded by earlier sprints. Idempotent — re-running
skips event generation if events already exist for the demo workspace.
This is internal demo data generated directly in the seed script (not
routed through the redirect/queue pipeline) — it does not appear anywhere
as if it were real production traffic.

## 11. Troubleshooting

**Analytics show zero clicks after clicking a link.** The worker
processes asynchronously — allow a second or two. Check Redis is running
(`redis-cli ping`) and that the `link-clicks` queue has no persistently
failed jobs (`redis-cli --scan --pattern 'bull:link-clicks:*'`).

**A specific endpoint returns 500.** Check the server log for the
originating SQL error — every aggregate query in `AnalyticsService` runs
as raw parameterized SQL, so a Postgres error message will name the exact
offending clause. (This is exactly how a real bug was caught during this
sprint's own verification: `getTopLinks`'s JOIN against `links` made an
unqualified `"workspaceId"` column reference genuinely ambiguous to
Postgres, since both tables have that column — fixed by qualifying every
generated column reference with a table alias. See
`analytics.service.spec.ts`'s "qualifies every WHERE-clause column..."
test, added as a regression guard.)

**Geographic data is all "Unknown."** Either `GEO_IP_PROVIDER=none` is
set, or `geoip-country` failed to load (check server startup logs for a
warning from `GeoipCountryProvider`) — both are graceful degradations,
not errors; redirects and event processing are unaffected either way.

**Unique visitor counts look higher than expected.** This is very likely
the by-design daily hash rotation (§4) — someone returning on a different
day is counted as an additional unique visitor. This is not a bug.
